下面我按你给出的“AI校园营养数字孪生系统”前端页面功能清单，直接整理出一套可用于后端设计评审的结果，包含两部分：第一部分是 API 需求表，第二部分是 MySQL 数据库表设计表。为了保证后续开发可执行，我不是按“页面一个接口”去机械拆，而是按真实业务对象、页面复用关系、数字孪生计算链路来设计。这样做的好处是接口不会碎片化，数据库也不会因为页面数量增加而失控。

这个系统的后端本质上围绕九类核心对象展开：用户账号、用户档案、健康目标、每日打卡、打卡明细、健康画像、趋势分析结果、预测与模拟结果、建议与消息提醒。前端十四个页面并不需要十四套彼此孤立的后端，而是复用同一套领域模型。也就是说，首页、健康画像页、趋势分析页、未来预测页、情景模拟页、个性化建议页，本质上都是围绕“用户基础信息 + 打卡历史 + 模型计算结果”做不同维度的读取与呈现。

上面这套接口已经能覆盖你列出的全部前端页面。接下来我给你后端接口设计上的一个关键建议：不要把“趋势分析”“预测”“画像”“建议”全部做成纯实时计算接口，否则会导致首页、画像页、预测页访问时压力很大，且同一批历史数据会被重复计算。更合理的做法是保留“结果表”，由每次用户打卡、更新基础信息、修改目标后触发增量计算，把结果写入数据库。前端查询时直接读结果表，这样性能和可维护性都会更好。

到这里，你已经有完整的 API 需求表和 MySQL 表头设计了。但为了让你真正能拿去做开发，我再把“页面与表、接口之间的映射关系”给你压缩说明清楚，这部分非常关键。

登录与注册页主要落在 user_account。个人基础信息页主要落在 user_profile。首页健康仪表盘不建议单独存一张首页表，而是通过 daily_checkin、digital_twin_profile、health_prediction_result、personalized_recommendation 聚合返回。健康打卡页的核心是 daily_checkin 作为主表，checkin_meal_record、checkin_exercise_record、checkin_body_record、checkin_sleep_record、checkin_habit_record 作为子表，这样最符合真实业务结构，也便于历史查询与模型训练。历史记录页直接查 daily_checkin 及各子表。健康画像页对应 digital_twin_profile。趋势分析页建议主要基于 daily_checkin 实时聚合，或者定时落表到 health_trend_snapshot。未来预测页对应 health_prediction_result。情景模拟页对应 scenario_simulation_record。个性化建议页对应 personalized_recommendation。健康目标页对应 health_goal 与 goal_progress_log。校园饮食推荐页对应 campus_canteen、campus_food_item、campus_diet_recommendation_log。消息与提醒页对应 notification_message 与 user_settings。个人中心页则汇总 user_account、user_profile、user_settings、achievement_record、daily_checkin。

如果你准备正式立项开发，我建议把接口再分成三类。第一类是事务型接口，比如登录、保存资料、保存打卡、更新目标。第二类是查询型接口，比如首页概览、历史记录、画像、趋势、消息列表。第三类是模型型接口，比如 AI 识别、预测、模拟、个性化建议生成。这样后端分层会很清晰：基础业务服务、统计聚合服务、模型服务。否则后面“预测”和“建议”很容易被硬塞进普通 controller，系统会变乱。

最后我给你一个更适合交付给开发团队的结论。若按最小可行版本实现，这个系统至少需要 22 到 30 个核心 API，12 到 18 张核心 MySQL 表。若你想先做 MVP，完全可以优先落地 10 张表：user_account、user_profile、user_settings、daily_checkin、checkin_meal_record、checkin_exercise_record、checkin_sleep_record、health_goal、digital_twin_profile、notification_message。然后在第二阶段再补趋势快照、预测结果、模拟记录、校园饮食推荐、成就系统。
